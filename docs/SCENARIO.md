# Scenario: The Last-Mile Dispatch Breach

## Fictional environment

Northstar Parcel Systems is a fictional logistics company operating a dispatch dashboard for simulated smart lockers and delivery robots. Support staff use a recovery workflow when a simulated unit stops reporting correctly. The dashboard receives live telemetry and recovery events over WebSockets.

The training environment contains only fabricated accounts, records, and device events. It does not model a real operator's infrastructure and must not issue commands to physical devices.

## Roles

- **Dispatcher:** views permitted operational telemetry and manages assigned recovery cases.
- **Support analyst:** investigates simulated unit incidents and requests recovery review.
- **Supervisor:** approves a recovery action within the simulated workflow.
- **Learner:** investigates the security boundary between users, sessions, subscriptions, and state transitions.
- **Simulator:** emits synthetic telemetry and records the result of approved lab actions.

## Intended chain

The final challenge should be a sequence of independently testable failures. The implementation must provide clear hints and observable evidence without requiring access to any real service.

1. **Event-channel authorization failure.** The learner discovers that a WebSocket connection can request a channel or subscription that the current identity should not be allowed to read. The result is limited to synthetic metadata.
2. **Object-level authorization failure.** A recovery record identifier exposed in the event stream is accepted without checking that the authenticated user owns or is assigned to that record.
3. **Stale connection after revocation.** A session is revoked, but an already established socket remains able to perform an action because authorization is only checked during the handshake or connection setup.
4. **Non-atomic approval workflow.** Two nearly simultaneous approval messages can pass a check-before-update sequence and cause duplicate simulated approval records or inconsistent state.
5. **Evidence and completion.** The learner submits a synthetic proof value generated by the server after the intended state transition. The server must validate completion; a client-side flag or hidden UI value is not sufficient.

Each stage should expose a clue that helps learners understand the business workflow. Avoid making the challenge depend on blind guessing or unexplained magic values.

## Optional extension: cross-site WebSocket abuse

A separate, opt-in extension may demonstrate why cookie-authenticated WebSocket handshakes need careful Origin validation and appropriate cookie settings. It must use a local-only mock victim and a local demonstration page. Do not target third-party sites or use real browser sessions.

## Intended evidence

The learner should be able to explain:
- which identity established the connection;
- which channel and object were requested;
- why that identity was or was not authorized;
- whether revocation was applied to an existing socket;
- how concurrent state changes were handled; and
- which server-side checks prevent the chain in secure mode.

## Completion criteria

A successful implementation should have:
- repeatable seed data and a reset operation;
- deterministic simulator events;
- a visible audit trail suitable for learning;
- tests for each individual weakness and the combined chain;
- secure-mode tests proving the corresponding controls reject the same actions; and
- no network dependency on external systems.

## Instructor note

Keep a separate solution guide for organizers if challenge secrecy matters. The public learner guide should explain the learning goals and safety boundaries without exposing every solution step or the completion value.
